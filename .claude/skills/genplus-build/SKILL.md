# GenPlus 项目构建工作流 (Build 模式)

本 Skill 专门指导 Agent 在 GenPlus 工作台中从零构建全新的企业级管理系统。

> [!IMPORTANT]
> **构建模式核心铁律**：
> 1. **严禁“一句话直接一干到底”**！即便用户给出的需求看似具体，也必须停下来执行交互式对齐确认。
> 2. 构建模式支持**两类设定**：
>    * **【简略模式】(Concise Mode)**：用户只需描述大致需求，AI 输出核心概要，与用户进行单轮对齐确认后，**其余所有底层细节由系统智能拟定**，直接自动化生成与启动！
>    * **【细节模式】(Detailed Mode)**：多阶段全流程精细研讨（基础信息 -> 实体关系 -> 逐字段规则 -> 动作矩阵天花板 -> 终审签署 -> 自动化落地）。
> 3. 当用户提出新需求时，若未明确模式，AI 优先呈递简明概要并询问用户希望以【简略模式】快速出原型，还是以【细节模式】深度定制。

## 阶段 0：环境感知与前置探活（跨平台动态检测与数据库门禁）

> [!CRITICAL]
> **跨平台感知与零硬编码铁律：**
> 严禁假定用户处于特定操作系统（如仅限 Linux 容器）或特定绝对路径（如 `/config/nuadmin`）！
> 在开始任何立项、建库建表、代码生成、数据播种或系统维护前，大模型**必须首先执行两步前置检查**：
>
> 1. **步骤一：检测操作系统与工作区根目录 (OS & RepoRoot Detection)**：
>    - **操作系统检测**：明确当前运行环境是 Windows (`win32`)、macOS (`darwin`) 还是 Linux (`linux`)。
>      * 可通过环境上下文或快速探测：`node -e "console.log(process.platform)"`。
>      * **跨平台执行适配**：
>        - Windows 环境：使用 `cmd.exe /c` 或 PowerShell，路径分隔符使用 `\` 或 Node 兼容的 `/`，npm 命令使用 `npm.cmd` 或通过 `{ shell: true }`，杀死进程树使用 `taskkill /PID <pid> /T /F`；
>        - Linux / macOS 环境：使用标准 bash / sh，杀死进程组使用 `process.kill(-pid)` 或 `lsof`/`ss`。
>    - **仓库根目录 `<repoRoot>` 检测**：动态获取当前工作区根目录（例如容器内 `/config/nuadmin`，Windows 下如 `J:\code\nuadmin` 或当前 workspace 根路径）。
>      * 后续所有脚本路径、环境配置文件与依赖目录，**一律以 `<repoRoot>` 动态拼接**（如 `<repoRoot>/scripts/check-db-connection.mjs`、`<repoRoot>/main-admin/.env`）。
>
> 2. **步骤二：动态探活与继承 MySQL 数据库连接**：
>    - **连接握手探活**：
>      * 运行探活脚本：`node <repoRoot>/scripts/check-db-connection.mjs`（脚本已内置跨平台与动态根目录自适应，回传当前 `platform`、`root` 与数据库在线状态）；
>      * 或调用 MCP 工具 `genplus_get_db_connection`（不传参，自动解析控制面配置并执行 ping 探活）；
>    - **确认环境连接配置**：
>      * 自动从 `<repoRoot>/main-admin/.env` 中读取并确认 `DB_HOST`、`DB_PORT`、`DB_USER`、`DB_PASS`、`DB_NAME`；
>      * 确认握手结果为 `ok: true`，保证 MySQL 实例在线且凭证有效；
>    - **配置动态继承与零硬编码**：
>      * 所有后续的数据库交互（包括子系统专属库 `nuadmin_t_*` 的建库校验、初始种子数据播种脚本、数据排查查询等），必须直接读取使用 `main-admin/.env` 的动态配置，彻底杜绝硬编码！
> 3. **主控生成器源码与编译纪律（严禁擅改 .output 产物）**：
>    - 主后台运行于 `main-admin/.output` 编译产物。若修改了主后台代码生成器（`server/utils/gen/*` 或 `shared/*`），**严禁直接在 `.output/` 临时产物中手工修补**！
>    - 必须在 `<repoRoot>/main-admin` 源码目录下执行 `npm run build` 进行工程级全量编译，并重启主后台服务，确保生成产物幂等、可维护、无环境漂移。
>    - 生成器生成子后台 `.env` 时，必须通过 `getControlPlaneDbConfig()` 动态继承真实宿主数据库配置，严禁回退至 127.0.0.1 或空密码。
> 4. **端口规划与主从联动铁律 (Port Convention & Registry)**：
>    - **主控制台 (Main Admin)**：默认运行于 `http://localhost:10000`（由 `<repoRoot>/main-admin/.env` 中 `PORT` 决定）；
>    - **子后台 (Sub Admin)**：默认从 `PORT + 1`（即 `10001`）起，按创建顺序自动递增分配空闲端口（`10001`, `10002`, `10003`...）；
>    - **用户自主指定端口与 AI 交互指引**：
>      * 用户若在对话中指定端口（如“端口使用 10086”），Agent 调用 `genplus_create_tenant` 时必须显式传入 `port: 10086`；
>      * 系统会自动进行端口合法性校验（1024~65535）、主控制台防冲突、租户库防重与宿主机动态探活；
>      * AI 在立项对齐与确认时，必须明确告知用户默认端口是哪个，并提示如何修改（如：“默认运行端口为 `http://localhost:10001`，若需自定义端口可直接说明”）。

## 路线 A：简略模式 (Concise Mode / 快速原型构建)

适用于用户想快速出原型、快速体验或不需要逐一斟酌每个字段细节的场景。

1. **生成《核心概要方案》**：
   Agent 根据用户粗粒度描述，智能推导核心骨架：
   - 系统名称与英文标识（如 `mp_qr_center`）；
   - 2~3 个核心业务实体与职责；
   - **智能装配推荐的能力库能力包（Capability Awareness & Matching，核心机制）**：
     * **前台触达场景**：
       - 二码 / 渠道推广 / 营销海报 / 获客引流 ➔ 智能预选 `landing_poster` (推广海报与二码落地页)
       - 报名 / 登记 / 预约 / 问卷 / 线索收集 ➔ 智能预选 `landing_form` (动态收集表单)
       - 招聘 / 职位 / 活动中心 / 展厅 / 咨询门户 ➔ 智能预选 `landing_portal` (前台复合门户: 列表+详情+表单)
       - 品牌官网 / 企业主页 / 资讯动态 / CMS ➔ 智能预选 `landing_cms` (企业官网与内容CMS)
     * **后台增强场景**：
       - 经营分析 / 关键指标 / 趋势图 ➔ 智能预选 `dashboard` (数据看板)
       - 状态枚举 / 业务字典 / 标签颜色 ➔ 智能预选 `dict` (数据字典)
       - 附件 / 头像 / 合同 / 图片存储 ➔ 智能预选 `file` (文件存储)
       - 审批流转 / 审核工单 ➔ 智能预选 `flow` (审批流)
   - 推荐的门禁模式（如 `rbac`）与皮肤色系（如 `macos-modern / emerald`）；
   - **运行端口规划**：明确展示分配的运行端口（如 `http://localhost:10001`，默认递增分配，并提示用户如需自定义可直接指定）。
2. **单轮交互式对齐确认**：
   向用户呈现精炼概要卡片（包含推荐的业务实体、能力包清单与运行端口），提示用户：“以上核心方向是否符合您的预期？确认后其余字段细节将由系统全自动推断并直接生成上线。（如需调整端口或其它设置可直接回复）”
3. **系统智能定策与全自动生成**：
   用户一旦确认，Agent **不再向用户繁琐提问**，立即由系统智能拍定：
   - 所有数据表的字段列表、主外键、类型（varchar/int/datetime/bool/money）；
   - UI 组件选型（input/select/date/switch/upload）；
   - 搜索筛选维度（like/eq/range）；
   - 动作矩阵与台账只读限制（如流水表禁止修改删除）；
   - 基础业务字典自动装配；
   - **执行能力库装配**：调用 `genplus_install_capability` 将已选的能力包（如 `landing_poster`, `dict`, `dashboard` 等）精准落库并写入配置！
   按序调用 MCP 工具（`create_tenant` -> `dict` -> `module` -> `fields` -> `design` -> `install_capability` -> `generate` -> `start` -> `screenshot`）一气呵成完成上线，交付访问链接与真机截图！

## 路线 B：细节模式 (Detailed Mode / 深度定制)

适用于企业级复杂业务、数据敏感、强审计规范或需要逐字段严格把控的系统。

### 阶段一：项目立项与基础信息对齐 (必须交互)

当用户选择细节模式时：

1. **主动向用户发起交互式立项问卷**（使用 `ask_question` 工具）：
   * **项目全称与英文标识**：向用户确认系统的正式中文名与英文标识（如 `wms` / `edu_asset` / `catering`）；
   * **运行端口（Port）**：告知用户默认从 10001 起自动分配空闲端口（如 `http://localhost:10001`），支持用户自主指定（如 `10086`）；
   * **核心应用场景与角色定位**：询问系统的主要使用群体与核心业务闭环；
   * **门禁模式（Auth Mode）**：
     - `rbac`（完整权限控制，角色 + Casbin 策略，生产推荐）
     - `users`（成员账号登录，统一权限）
     - `simple`（单一轻量门禁口令）
   * **视觉皮肤与色系**：
     - 皮肤风格：`macos-modern`（macOS 现代感微拟物）、`classic`（企业稳重）、`minimal`（极简清新）
     - 主题色调：`blue`（科技蓝）、`emerald`（生机绿）、`violet`（优雅紫）、`amber`（暖阳橙）

等待用户反馈提交后再进入下一阶段。

### 阶段二：业务实体与模块划分研讨 (需求方案草案)

收到用户录入的基础信息后，Agent 需拟定业务实体草案，并**再次与用户研讨确认**：

1. **分组与模块划分**：
   * 将系统划分为 1~3 个业务分组（如：基础数据、业务流转、统计报表）；
   * 在每个分组下设计具体数据模型（表名、主键、业务字段）；
2. **枚举字典规划**：
   * 提炼需要配置的标准字典（如状态字典、类型字典、审核结果字典）；
3. **输出方案卡片并征求用户反馈**：
   * 罗列模块清单、核心字段与对应关系；
   * 询问用户：“这个模块划分和字段规划是否满足您的需求？是否有需要增加或删减的实体？”

## 阶段三：两级能力天花板与动作矩阵确认 (安全与审计设计)

根据 GenPlus 两级能力天花板架构，必须与用户确认每个模块的**物理能力上限**：

1. **明确只读 / 审计模块**：
   * 诸如“操作日志”、“库存流水台账”、“财务对账单”等审计类模块，建议物理关闭 `create`、`edit`、`delete`，仅保留 `export` 和 `detail`；
   * 询问用户是否同意该模块的只读限制；
2. **确认常规业务模块的动作全集**：
   * 是否支持 `export`（导出）？
   * 是否需要 `batch`（批量操作）？
3. **确认能力库装配矩阵 (前台触达与后台增强，拒绝纯单薄CRUD)**：
   * **前台触达能力 (B+C 双端业务闭环)**：
     - `landing_poster`：是否需要 C 端推广落地页、扫码 PV 统计与后台“推广码”弹窗？
     - `landing_form`：是否需要面向用户的公开动态收集表单（线索收集、预约登记、活动报名）？
     - `landing_portal`：是否需要前台检索、卡片列表与在线提报复合门户（招聘门户、展厅、活动中心）？
     - `landing_cms`：是否需要企业官网大屏、核心特性网格与资讯文章系统？
   * **后台系统增强能力**：
     - `dashboard`：是否需要首页经营分析大屏与核心指标聚合卡片？
     - `dict`：是否需要数据字典集中维护与状态联动？
     - `file`：是否需要文件、图片与附件存储？
     - `flow`：是否需要多级工单审批流？
     - `io` (导入导出) / `batch` (批量操作) / `tree` (树形层级) / `recycle` (软删回收站) / `job` (定时任务) / `message` (站内信) / `security` (水印加固) / `print` (单据打印)。

## 阶段四：方案终审门禁 (Gate Review & Sign-Off)

在调用任何生成工具前，Agent 必须向用户呈现一份结构化的《项目构建终审蓝图》：
* **基本信息**：系统名称、运行端口（如 `http://localhost:10001`，自主指定或系统自动分配）、数据库名、门禁模式、皮肤色系
* **字典清单**：包含的所有枚举项与色彩
* **分组与模块**：各模块名称、表名、字段清单、动作矩阵上限
* **系统扩展能力**：已选装的能力包
* **前台触达微页面**：若装配了 landing 能力，说明前台访问路径与功能

明确提示：“【构建门禁】以上为即将构建的完整蓝图，请确认是否立即执行建档生成？”
**只有在用户明确确认（例如点击同意或回复“确认执行”）后，才能进入阶段五！**

---

## 阶段五：执行自动化构建与真机校验 (调用 GenPlus MCP)

获得用户正式签署后，按顺序调用工作台 MCP 工具：
1. `genplus_create_tenant`：创建项目档案；
2. `genplus_save_dict`：逐组录入业务枚举字典；
3. `genplus_create_model_group`：建立模块分类分组；
4. `genplus_create_module` & `genplus_add_fields`：创建业务模型与字段；
5. `genplus_configure_design`：写入皮肤配置与动作能力矩阵；
6. `genplus_install_capability`：逐项安装并配置确认的能力包（支持传入配置对象）；
7. `genplus_generate_project`：触发生成站编译并导出完整源码；
8. `genplus_manage_service`：启动子后台独立实例（`action: 'start'`）；
9. **真机全链路冒烟门禁 (Mandatory Verify Gate)**：
   - **9.1 API 契约与环境冒烟**：调用 `/api/verify/:tenantId`（`boot: true`）执行全面冒烟检测，严格要求所有用例（工程结构、TypeScript 语法、物理建表、Cookie 租户隔离、组件具名槽、真实登录与能力探针）`fail=0` 且 `skip=0` 全部通过；
   - **9.2 侧边栏与 UI 导航可用性铁律 (Sidebar Anti-Lockout Gate)**：
     * **展开态中文字宽防截断**：侧边栏展开宽度必须锁定为最小 240px（`:default-size="19"`，min-w 240px），确保 6~8 汉字长度的菜单（如“热门网页周监测”、“站点档案矩阵”）完整呈现，严禁出现省略号截断（`...`）；
     * **双重折叠/展开保活 (防单向闭锁死循环)**：
       - `AppSidebar.vue` 底部的折叠按钮 `<UDashboardSidebarCollapse>` **严禁包裹在 `v-if="!collapsed"` 条件块内**！在折叠态下必须居中常驻，确保随时可反向展开；
       - `AppTopbar.vue` 顶部栏左侧（`#left`）必须标配联动折叠按钮，形成顶部与底部的双保险控制入口；
     * **折叠态扁平化与幽灵空项清除**：折叠时必须将菜单打平为 `flatItems`，剥离 `type: 'label'` 分组标头，消除 Nuxt UI 渲染的残余空 `<li>` 占位和错位；折叠时底部用户头像必须优雅收拢，严禁退化为无意义省略号；
     * **真机折叠/展开动态测试**：必须在无头浏览器中实际执行一次“点击折叠 -> 断言平滑收起为图标条且展开按钮依然存在 -> 点击展开 -> 断言成功还原为展开态”，杜绝单向死锁；
   - **9.3 表格列宽人体工学铁律 (Table Column Ergonomics Gate)**：
     * **主键/ID 列紧凑约束**：主键或纯数字 ID 列宽度必须显式限定为紧凑窄列（`72px ~ 80px`，居中对齐），严禁任由表格自适应分配导致单个 2 位数字占用 15%~20% 容器宽度的反常识巨大留白；
     * **状态/枚举字典列**：宽度锁定为紧凑居中（`100px ~ 110px`）；
     * **时间/日期列**：日期锁定 `130px`，日期时间锁定 `170px`；
     * **操作列**：锁定右侧紧凑（`140px ~ 160px`，居右对齐）；
     * **主业务文本列**：标题、名称、路径等必须设为弹性自适应伸展（`min-w-[150px]`），确保视觉重心聚焦于核心业务数据；
   - **9.4 搜索栏防挤压与安全间距铁律 (Search Filter Ergonomics Gate)**：
     * 搜索区域必须采用带换行保护的响应式弹性流式排版（`flex-wrap gap-x-4 gap-y-3`）；
     * 搜索字段容器严禁设置过窄的固定像素；数值步进器（带有 +/- 按钮）、日期选择器等复合组件，容器宽度必须保底 `>= 200px`，且内部必须设置 `min-w-0` 防溢出；
     * 搜索字段超过 4 项时，严禁横向硬挤导致元素重叠遮挡；“查询/重置”按钮组必须具备独立的 `shrink-0` 外边距保护，严禁被前一个输入框挤压侵占；
10. **数据库与数据检验**：调用 `genplus_db_query` 检查物理表结构与初始种子数据；
11. **真机画面截图与多模态视觉质检自愈闭环 (Mandatory Visual QA & Self-Correction Loop)**：
    - 调用 `genplus_take_screenshot` 截取真实运行画面；
    - **最高铁律：截图不是交差的任务终点，而是闭环质检的判定门禁！**
    - Agent 在截取画面后，**严禁未经任何审视直接交差甩图给用户**！Agent 必须调用自身视觉多模态能力或 DOM 碰撞检测执行【4 项视觉健康自检清单】：
      1. 【侧边栏审视】：展开态中文菜单是否完整展示、无省略号截断；折叠态是否对齐整洁、无幽灵空位；
      2. 【搜索区审视】：搜索框组件之间是否有重叠、文字挤压、输入框边界相撞；
      3. 【表格列宽审视】：主键列是否窄而紧凑（不得出现数字小但宽度巨大的反常识大间隙），长文本是否获得合理分配；
      4. 【状态异常审视】：是否有未捕获的报错弹窗、死锁状态或页面白屏。
    - **违规自愈铁律（Self-Correction Mandate）**：
      * 一旦在视觉审阅中发现上述任何瑕疵，**该构建任务立即判定为失败（Fail），严禁直接交付用户**！
      * Agent 必须自动定位模板/样式诱因，就地实施代码修正，重新生成编译并重新截图验证，**直至自检达到 100% 商业级高可用视觉标准后方可交付用户**！
    - **交付时必须呈递双态证据**：
      * 证据一：**展开态全景截图**（验证中文字段完整、无省略号截断、导航层级分明）；
      * 证据二：**折叠态图标精简截图**（验证折叠图标排列整洁、无幽灵空白空项、展开按钮常驻可用）；
      * 证据三：核心业务大屏/表单页面真机截图；
12. 向用户汇报访问链接、账号凭证、数据库连接串与多态预览截图。

## 阶段六：B端中台 + C端微页面一体化 (Front+Back Dual-End Cohesion / 可选扩展)

当业务场景涉及对外公开页面（如公众号渠道二维码展示与扫码推广、问卷登记、活动报名、公开商品展示页等）时：
1. **自动规划 C端路由与免鉴权接口**：
   - 页面路由：如 `/p/[scene]` 或 `/p/[id]`，采用免登录的独立移动端卡片布局（`definePageMeta({ layout: 'blank' })`）；
   - 服务端接口：在 `server/api/public/*` 开放轻量免鉴权 API（如二维码 Base64 生成、模拟扫码回调、公开登记提交）；
2. **打通数据闭环**：
   - C端用户行为（扫码/提交）即时写入 B端后台数据台账（如 `mp_scan_log`），并原子自增业务主表计数器；
   - B端后台数据表格（如 `/admin/channelQrcode`）在操作列提供一键直达“推广页”快捷按钮；
3. **调用 MCP 落地与验证**：
   - 调用 `genplus_create_public_landing` 一键建立 C端微页面模板与公开 API；
   - 调用 `genplus_take_screenshot` 对 `/p/:scene` 拍摄真机移动端预览截图，交付完整商业闭环！
